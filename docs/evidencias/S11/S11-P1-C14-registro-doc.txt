4. PURGA TRAS SIGKILL (DeregisterCriticalServiceAfter)

$ docker kill -s KILL infra-doc-service-1     (03:05:40 UTC)
t+10s entries=1
t+20s entries=1
...
t+60s entries=1
t+70s entries=0

Observacion honesta: la entrada tarda ~70 s, no <=60 s, porque el cronometro
de 1m de DeregisterCriticalServiceAfter empieza cuando el check pasa a
critico (deteccion ~10 s con interval 10s / timeout 3s), no en el instante
del kill. Es el comportamiento documentado de Consul con el valor `1m` que
fija la tarea; el catalogo queda limpio sin intervencion manual.
Nota: esta medicion se tomo con el binario previo al reintento; la purga la
ejecuta el agente y no depende del codigo de doc-service.

5. ARRANQUE CON CONSUL CAIDO (degradacion)

$ docker compose --env-file .env -f compose/docker-compose.yml --profile full stop consul-agent consul
$ docker compose ... up -d --no-deps --scale doc-service=1 doc-service
(sleep 25)

$ wget -qO- http://127.0.0.1:8080/healthz     (dentro del contenedor)
{"status":"healthy","timestamp":"2026-11-18T03:16:41Z","service":"doc-service"}

$ wget -qO- http://127.0.0.1:8080/metrics | grep ^docservice_consul_registration_failed_total
docservice_consul_registration_failed_total 3

$ docker logs infra-doc-service-1 | grep -c "registro en Consul fallido"
3

El servicio arranca y sirve sin Consul. Cada intento fallido loguea WARN con
id, address y error, e incrementa la metrica. Ejemplo del primer intento:
{"level":"WARN","msg":"registro en Consul fallido, el servicio sigue operando",
 "id":"doc-service-31606a5d9624","address":"172.22.0.8",
 "error":"consul register: Put \"https://consul-agent:8501/v1/agent/service/register\": dial tcp: lookup consul-agent on 127.0.0.11:53: server misbehaving"}
(En modo degradado, sin DNS del agente, la derivacion de direccion cae al
primer IPv4 global y puede devolver la IP de la red `data`. No importa: en ese
estado no hay registro. Cuando el agente responde, usa la IP de `internal`.)

La replica se registra sola cuando Consul vuelve, con backoff 5 s -> 60 s.
Sin este reintento la replica quedaba fuera del catalogo hasta que alguien la
reiniciara.

Cambios de infraestructura acompanantes (justificados):
  - infra/compose/consul/config/agent.hcl: se agrega `client_addr = "0.0.0.0"`.
    Con el default 127.0.0.1, el agente solo escuchaba en loopback y ningun
    contenedor de `internal` podia registrarse contra el (medido:
    `netstat -ltn` -> 127.0.0.1:8501 y `connect: connection refused` desde
    doc-service). No se publica al host: el bloque compose del agente no tiene
    `ports:`.
  - doc-service y doc-service-canary reciben CONSUL_REGISTRATION_ADDR,
    SERVICE_NAME y el secreto consul_doc_service_token; el canary ademas
    CONSUL_HTTP_ADDR/CACERT/TOKEN_FILE, que no tenia. Nota: antes del cambio el
    cliente KV del canary usaba el default interno del binario
    (https://consul-agent:8501), que tambien funciona; ahora queda explicito.

Rollback verificado por diseno (no ejecutado para no dejar el entorno sin
registro): CONSUL_REGISTRATION_DISABLED=true hace que Register y Deregister
sean no-op y que el loop de reintento no arranque (cubierto por
TestDisabledSkipsHTTP).
