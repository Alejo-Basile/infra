El desregistro consume como maximo 2 s dentro del presupuesto de 6 s
(SHUTDOWN_GRACE_SECS); el resto es el drenaje HTTP/consumer ya existente.

Observacion honesta: durante la ventana de pruebas aparecio una entrada
`c1a407ae-067c-37f4-2dda-8759563eddf3` con ServiceName svc-extraction-worker.
No la crea este cambio (el ID del worker es `<servicio>-<hostname>`): es estado
persistido de pruebas previas en el volumen consul-agent-data. Se purgo sola
tras pasar su check a critico y no reaparecio despues. El ID creado por este
cambio es siempre `extraction-worker-<hostname>`.

4. PURGA TRAS SIGKILL (DeregisterCriticalServiceAfter)

t+90s all_entries=0

El cronometro de `1m` empieza cuando el check pasa a critico (~10 s de
deteccion con interval 10s / timeout 3s), de ahi el margen sobre 60 s. El
catalogo queda limpio sin intervencion manual.

5. ARRANQUE CON CONSUL CAIDO (degradacion)

$ docker compose ... stop consul-agent consul
$ EXTRACTION_WORKER_IMAGE=extraction-worker EXTRACTION_WORKER_TAG=local \
  docker compose ... up -d --no-deps --scale extraction-worker=1 extraction-worker

$ curl -fsS http://127.0.0.1:8081/healthz
{"status":"ok"}
$ curl -fsS http://127.0.0.1:8081/metrics | grep ^worker_consul_registration_failed_total
worker_consul_registration_failed_total 3
$ docker logs infra-extraction-worker-1 | grep -c "registro en consul fallido"
3

El worker arranca, sirve /healthz y no bloquea: el registro se reintenta con
backoff 5 s -> 60 s y cada fallo loguea WARN e incrementa la metrica.

la IPv4 de `internal`.
