4. Recreación y permisos (bug encontrado en C06)

El contenedor se recreó: `docker compose --env-file ../.env --profile full up -d prometheus`
  => Container infra-prometheus-1 Recreated / Started
`docker exec infra-prometheus-1 ls /run/secrets` => consul_ca_cert, consul_prometheus_token

Bug: consul-bootstrap-acl.sh escribe los tokens con `chmod 600`, y el file-secret
de Compose propaga el modo del archivo del host. Prometheus corre como `nobody`
(65534) y no podía leer el token:
  err="unable to read authorization credentials: open /run/secrets/consul_prometheus_token: permission denied"
  (repetido cada 15 s en el discovery manager de Consul)
Corrección aplicada: `chmod 0644 infra/secrets/consul_prometheus_token.txt`
(consistente con consul_operator_token.txt y el resto de secretos consumidos por
contenedores). Tras el chmod, `docker exec -u 65534 ... head -c 4` lee el token.
DEUDA PARA C11-C14: consul-bootstrap-acl.sh:119,127 deja en 600 los tokens
`consul_doc_service_token`, `consul_ratelimitd_token` y `consul_worker_token`.
Los tres servicios consumidores corren como usuario no-root y van a fallar la
lectura igual que Prometheus. Hay que fijar el modo (644) o inyectarlos con otro
mecanismo antes de C14/C18.

porque el puerto 9090 no se publica al host: la red `internal` es internal:true)
  job=consul  instance=consul:8501
  scrapeUrl=https://consul:8501/v1/agent/metrics?format=prometheus
  health=up  lastError=""  lastScrape=2026-11-17T23:43:09Z

Query de cordura del gauge de líder (PromQL):
  max({__name__=~"consul_.+_server_isLeader"}) => 1

Se scrapea el SERVER (consul:8501) y no el agente: agent.hcl no define
`client_addr`, así que consul-agent escucha solo en loopback y rechaza conexiones
desde otras redes (`consul-agent:8501` => connection refused). Es un gap de C04
que no bloquea C08 pero sí bloquea el registro de apps de C14/C18, que apuntan al
agente. Además /v1/agent/metrics devuelve JSON por defecto: se requiere
`params: {format: [prometheus]}`.

9. Estado de alertas al cierre y dependencias pendientes (honesto)

- Firing: DocServiceNotReady y WorkerDown. Causa: app-services todavía no tiene
  targets porque C14/C18 no registran svc-doc-service / svc-extraction-worker. Se
  migraron a `absent(up{job="app-services", service="..."} == 1)` justamente para
  no quedar en NoData silencioso; se apagan solas cuando C14/C18 cierren.
- DLQNotEmpty ya estaba firing antes de esta tarea (hay mensajes en la DLQ); no lo
  introduce este cambio.
- ConfigKVStale y ConfigKVRejected quedan NoData hasta que C11-C13 publiquen
  `*_config_kv_last_success_timestamp_seconds` y `*_config_kv_rejected_total`; los
  selectores son regex agnósticos al prefijo para que funcionen sin retoques.
- ConsulNoLeader no usa `consul_raft_leader`: esa métrica no existe en Consul
  1.22.7. El gauge real es `consul_<nodo>_server_isLeader` (prefijo de nodo
  inestable), de ahí el selector regex.
- El puerto 9090 de Prometheus no se publica al host porque el contenedor está en
  la red `internal` (internal:true). Las consultas de evidencia se hicieron desde
  un contenedor efímero en infra_internal contra http://prometheus:9090.
