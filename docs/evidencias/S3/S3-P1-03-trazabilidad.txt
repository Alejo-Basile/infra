1. Objetivo
-----------
Que un correlation_id enviado por el cliente (o generado por doc-service en el
primer request) sea rastreable a través de toda la cadena:

  Traefik access log -> doc-service logs -> MongoDB
  (documents.correlation_id + historial por transición) -> Redis Streams
  (campo payload)

Decisiones de diseño verificadas:

- Traefik OSS no puede generar UUIDs (no existe un middleware nativo para
  ello). doc-service genera el correlation_id en el primer request que llega
  sin header válido (SPEC §10). traefik.yml conserva `X-Correlation-Id: keep`
  en el access log con un comentario aclarando que solo preserva un valor
  inbound. No se agregó plugin, ForwardAuth ni middleware con header vacío.
- Contrato del header: constante Go `X-Correlation-ID` (los docs y curl usan
  `X-Correlation-Id`; los headers HTTP son case-insensitive). Validación:
  TrimSpace, máximo 128 caracteres, charset `^[A-Za-z0-9._:-]+$`. Si falta o
  es inválido, se genera UUID v4. El warning solo loguea el largo del valor
  crudo, nunca su contenido (sin inyección de logs ni fuga de datos).
- Webhook (`/internal/storage/events`; la mención de SPEC §9 a
  `/internal/documents/{id}/uploaded` está desactualizada): carga el documento
  ANTES de leer MinIO; si no existe o no está en PENDING_UPLOAD responde
  `200 no_transition` sin I/O de objetos. Las transiciones usan
  UpdateStatusWithHistory con actor `minio-webhook`, el correlation_id del
  documento (fallback al del request), reason `NOT_A_PDF` al rechazar. Los
  logs llevan correlation_id y request_correlation_id.
- Mensaje de Redis: la entrada del stream tiene exactamente UN campo `payload`
  cuyo JSON contiene exactamente document_id, object_key, correlation_id,
  enqueued_at y schema_version (1). Sin `attempts` (el delivery count vive en
  XPENDING, SPEC §5.4). Discrepancia conocida: SPEC §5.4 muestra un XADD plano
  con campos individuales; la implementación conserva el envelope `payload`.
  Queda como follow-up de alineación de SPEC, no como cambio de código.
- La imagen de doc-service se reconstruyó localmente como `doc-service:local`
  (override compose/docker-compose.build.yml) para el E2E.

3. Hallazgo 401: aislamiento, causa raíz y fix
-----------------------------------------------
La primera corrida del E2E falló en los pasos de Mongo/Redis: el documento
quedaba en PENDING_UPLOAD y no aparecía ningún mensaje en Redis.

Log de MinIO:
  Error: http://doc-service:8080/internal/storage/events returned
  '401 Unauthorized', please check your endpoint configuration
  (targetID="docservice:webhook")
Log de doc-service:
  webhook: token inválido o ausente

Aislamiento:
- POSTs sintéticos desde el contenedor minio hacia doc-service: token Bearer
  válido = 200, token incorrecto = 401, sin token = 401. El handler estaba
  sano.
- Comparación de entorno por sha256 (sin imprimir valores):
  `MINIO_NOTIFY_WEBHOOK_AUTH_TOKEN_DOCSERVICE` de minio ==
  `MINIO_WEBHOOK_SECRET` de doc-service ==
  secrets/minio_webhook_secret.txt.

Causa raíz: el evento del bucket estaba suscrito al target gestionado por mc
(`docservice`), cuya config persistida no tenía auth_token APLICADO al proceso
en ejecución. `mc admin config set` escribe en el config store, pero MinIO solo
aplica la config de notificaciones al reiniciar, y la verificación del script
viejo solo grepeaba `endpoint=`, por lo que saltaba el restart. El target
declarado por env en compose (`DOCSERVICE`, con el token correcto, aplicado en
cada arranque de minio) existía pero no tenía suscripción.

Evidencia de la sonda: mientras ambas suscripciones coexistieron brevemente,
cada subida de prueba produjo exactamente un 401 (target legacy) y un 200
(target DOCSERVICE) en los logs de doc-service (user agent Go-http-client),
probando que el target por env envía el Bearer correcto. Los objetos de la
sonda usaron keys sin el prefijo raw-pdfs/ y el handler los filtró como
prefijo incorrecto (200, silencioso en debug); la autenticación quedó probada
por el par 401/200, y la corrección completa por el E2E final verde.

Fix (commit 6359133):
- compose/minio/init-notifications.sh ya no gestiona el target con
  `mc admin config set`. Verifica que el target declarado por compose
  (DOCSERVICE) esté registrado, retira la suscripción legacy si existe
  (`mc event remove <ARN-visible> --event put`) y suscribe ObjectCreated:Put
  a DOCSERVICE. El job elimina el mount de minio_webhook_secret que quedó sin
  uso.
- El target legacy de mc sigue registrado en el config store pero sin
  suscripción (inerte); el job retira cualquier suscripción legacy re-agregada
  en cada corrida.
- Migración probada en vivo: se re-agregó deliberadamente la suscripción
  legacy y luego:

    docker compose ... run --rm minio-notify-init
    -> Suscripcion legacy retirada: arn:minio:sqs:us-east-1:docservice:webhook
    Lista final de eventos:
    arn:minio:sqs:us-east-1:DOCSERVICE:webhook   s3:ObjectCreated:*

- Ambos scripts init ganaron el helper POSIX `resolve_secret`: lee secretos
  `${VAR}_FILE`, falla en voz alta si falta o queda vacío, nunca imprime
  valores. Antes, minio-init salía 1 y notify-init podía fijar un auth_token
  vacío porque compose pasa variables `*_FILE`.

5. Decisiones
--------------
- Generación del correlation_id en doc-service (primer request), no en
  Traefik: Traefik OSS no genera UUIDs; SPEC §10 ya prevé esta alternativa.
- `X-Correlation-Id: keep` se mantiene en el access log con comentario
  aclaratorio; sin plugins ni middlewares nuevos en S3.
- Envelope `payload` JSON en Redis (un solo campo) en lugar del XADD plano de
  SPEC §5.4; contrato fijado por test estricto; alineación de SPEC como
  follow-up.
- El webhook valida el documento antes de leer MinIO (200 no_transition sin
  I/O) e histórica cada transición con actor `minio-webhook`.
- Fix de notificaciones: suscribir el target declarado por compose (env, se
  aplica en cada arranque) y retirar la suscripción legacy de mc, en lugar de
  depurar el config store persistido de mc.
- `resolve_secret` POSIX en ambos scripts init: soporte `*_FILE`, fallo
  explícito en vacío, sin imprimir secretos.

7. Follow-ups (no son bloqueos abiertos)
-----------------------------------------
- `.env` local: `REDIS_STREAMS_PASSWORD` difiere de
  secrets/redis_streams_password.txt (el redis-streams en ejecución usa el
  archivo de secretos); e2e-correlation.sh lee `secrets/`, no `.env`.
  Higiene local: alinear y nunca commitear `.env`.
- El token del webhook de minio viene de `.env`
  (MINIO_WEBHOOK_SECRET -> MINIO_NOTIFY_WEBHOOK_AUTH_TOKEN_DOCSERVICE)
  mientras doc-service lee /run/secrets/minio_webhook_secret: mantener ambos
  alineados; al rotar, recrear minio
  (`docker compose up -d --force-recreate minio`), un restart simple no
  refresca el env.
- Sentinel 1/2/3 siguen en Restarting (deuda de S2, fuera de alcance).
- Alinear la redacción de SPEC §5.4 (XADD plano) con el envelope `payload`
  implementado; cambio de documentación, no de código.
- E2E real del worker de extracción: S4-P1-01.

8. Conclusión
--------------
- El correlation_id es rastreable de extremo a extremo en la cadena existente:
  Traefik access log, logs de doc-service, Mongo (documento + historial) y
  payload de Redis Streams.
- Sin header, o con header inválido, doc-service genera UUID v4 y el valor
  crudo inválido no aparece ni en responses ni en logs.
- El webhook queda suscrito únicamente al target declarado por compose
  (DOCSERVICE), con token aplicado en cada arranque; la suscripción legacy de
  mc quedó inerte y el job de init la retira de forma idempotente.
- El paso del worker es N/A en este alcance (S4-P1-01); el contrato del
  mensaje quedó fijado por test.

9. Revisión nativa (RDD, gentle-ai review)
------------------------------------------
Los dos slices se revisaron con el ciclo nativo de review (consent del humano:
"Revisar este cambio") y ambos quedaron APROBADOS con la autoridad quemada:

  doc-service  lineage review-db63df1eef2e3118  revision c59bc035...  (approved + acknowledged)
  infra        lineage review-e0fc16f82f05af69  revision 4e0e3487...  (approved + acknowledged)

Lentes: doc-service review-risk + review-reliability; infra review-risk +
review-resilience. 8 advisories, 0 BLOCKER/CRITICAL: ninguno abrio correccion
ni reabre el review.

- R1 (charset del header): un X-Correlation-ID con '=', '+', '/', '%' o espacios
  internos se descarta y se reemplaza por UUID v4. Es el hardening acordado
  (spec S1); conviene confirmar que los productores legitimos de trace IDs
  encajan en [A-Za-z0-9._:-].
- R3 (failure_reason del REJECTED): el reviewer no vio el adapter Mongo
  (preexistente, fuera del candidato). `UpdateStatusWithHistory` setea
  `failure_reason` desde `entry.Reason` cuando el destino es REJECTED / FAILED /
  EXTRACTION_FAILED, asi que el campo top-level se sigue persistiendo.
- R3 (texto del log de REJECTED) y R3 (asercion de un solo campo en el
  payload): cambios de texto/estrictez ya asumidos; la asercion existe
  justamente para fijar el contrato que consumira el worker.
- R1 (secretos en argv del E2E): `mongosh -p` y `redis-cli -a` exponen las
  credenciales locales en el process table del host durante la corrida. El
  impacto queda acotado al host de desarrollo (las mismas credenciales ya estan
  en archivos locales que el operador lee). Follow-up: pasar la password por
  variable de entorno o archivo de config.
- R1 (chequeo de presencia del token en el job): el job verifica el registro
  del target y su endpoint, no la presencia del auth_token. Un token ausente se
  manifiesta como 401 en doc-service (fail-closed), tal como registro la sonda.
- R4 (patron del chequeo de endpoint): el reviewer sostuvo que el AVISO de
  `ENDPOINT_${TARGET}=` dispara en cada corrida. Verificado en vivo: la corrida
  limpia del job NO emite AVISO (mc ecoa la variable de env
  `MINIO_NOTIFY_WEBHOOK_ENDPOINT_DOCSERVICE=...` y el patron matchea). Queda
  como robustez a futuro: aceptar tambien la forma `endpoint=` de mc.
