## Escenario

- Host: 4 nucleos. Worker: imagen `extraction-worker:s5-p4-01-hol3`, `WORKER_MAX_CONCURRENCY=4`.
- Stream `stream:pdf-processing`, grupo `extraction-workers`.
- Objeto: `raw-pdfs/loadtest/heavy.pdf`, 400 paginas de texto, 1,6 MB (valido, extraible).
- Sembrado a las **01:58:06 UTC**: 700 documentos `QUEUED` + 700 mensajes `XADD` con el
  contrato completo (`document_id`, `object_key`, `correlation_id`, `enqueued_at`,
  `schema_version=1`). **0 workers corriendo en ese momento.**

Estado al sembrar: `lag=700`, `PEL=0`, `XLEN=1297` (XLEN incluye entradas historicas).

## 1. La alerta dispara

Regla (`compose/prometheus/alert.rules.yml`):

```
QueueDepthHigh = (redis_stream_group_lag + redis_stream_group_messages_pending) > 500
for: 5m
```

```
02:03:11 UTC  QueueDepthHigh -> firing   (lag=700, PEL=0)
              Alertmanager POST /api/v2/alerts: recibida
              summary: "Cola pdf-processing con mas de 500 documentos pendientes por 5m"
```

La ventana `for: 5m` se respeto: siembra 01:58:06 + 5m = 02:03:06, firing 02:03:11.

## 2. Runbook: escalar y medir

Metrica de drenaje usada (la correcta): **`lag + PEL`** = no entregado + entregado sin
confirmar. `XLEN` no sirve (nunca baja) y `lag` solo tampoco (ver hallazgo H1).

```bash
# paso 1: escala a 1
docker compose -f compose/docker-compose.yml --env-file .env --profile full \
  up -d --scale extraction-worker=1 extraction-worker      # 02:04:02
```

## Hallazgos del ensayo (accionables)

### H1 — `lag` solo resuelve la alerta antes de tiempo

A las 02:04:16, con **443 de 700 documentos aun `QUEUED`**, `lag` ya marcaba **0**: el
reader hace prefetch y Redis considera "entregado" lo que todavia no se proceso. Una
alerta basada solo en `lag` habria pasado a `inactive` con dos tercios del trabajo
pendiente. Por eso la regla usa **`lag + PEL`**.

### H2 — Escalar 1 -> 4 no aumento el throughput en este host

2,23 docs/s con 1 worker vs 2,13 docs/s con 4. Causa: el host tiene **4 nucleos** y cada
worker corre con `WORKER_MAX_CONCURRENCY=4`; un solo worker ya satura la CPU con
extracciones de 400 paginas. Consecuencia para el runbook: `N` no debe superar
`nucleos / concurrencia_por_worker` para cargas CPU-bound. Escalar mas solo agrega
contencion de CPU y consumidores ociosos.

### H3 — XLEN es monotonico

`XLEN` paso de 77 a 577 a 1297 y nunca bajo al consumirse; las entradas permanecen hasta
`XDEL`/`XTRIM`. Cualquier alerta o criterio de "la cola baja a la mitad" medido con XLEN
es inmedible por construccion.

### H4 — El exporter SI publica las series de stream

La version anterior de esta evidencia afirmaba que `redis_stream_*` tenia 0 series. Es
falso: `redis_exporter:v1.93.0` publica `redis_stream_length`,
`redis_stream_group_lag`, `redis_stream_group_messages_pending`,
`redis_stream_group_consumers` y `redis_stream_length` de la DLQ. No hizo falta agregar
`--check-single-streams`.

### H5 — Sentinel estaba en crash-loop por overlay corrupto

Durante el ensayo las 3 instancias de Sentinel estaban en `Restarting` con
`cannot create /tmp/sentinel.conf: Permission denied` (409 reinicios). Misma imagen y
mismos mounts en un contenedor nuevo escriben `/tmp` sin problema: capa overlay
corrupta de esas instancias (secuela del disco lleno). Se resolvio con
`--force-recreate`; quorum 3/3 verificado apuntando a `redis-streams:6379`.

## Como reproducir

1. Objeto valido en `raw-pdfs` y N documentos `QUEUED` en Mongo con el mismo `object_key`.
2. `--scale extraction-worker=0`.
3. `XADD` N mensajes con contrato completo.
4. Esperar `for: 5m` y confirmar `QueueDepthHigh` en `firing`.
5. Seguir `runbooks/escalado-worker.md` midiendo `lag + PEL`.
6. Confirmar `COMPLETED` en Mongo y cerrar con `--scale extraction-worker=1`.

`S5-P1-02` queda **CERRADA**: la alerta existe, dispara y se resuelve; el runbook se
ejecuto y el DoD se cumple. Quedan dos acciones de seguimiento fuera de alcance:
