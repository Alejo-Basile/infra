### S1a — Secreto del webhook MinIO -> doc-service (SPEC §5.2, §9)
Antes: el token viajaba interpolado en texto claro en 3 puntos:
  - minio: MINIO_NOTIFY_WEBHOOK_AUTH_TOKEN_DOCSERVICE: ${MINIO_WEBHOOK_SECRET}
  - doc-service: MINIO_WEBHOOK_SECRET: ${MINIO_WEBHOOK_SECRET}
  - minio-notify-init: sin el secreto montado (el script fallaba: "MINIO_ROOT_PASSWORD requerido")

Después:
  - minio: secret `minio_webhook_secret` + wrapper de entrypoint que exporta
    MINIO_NOTIFY_WEBHOOK_AUTH_TOKEN_DOCSERVICE desde /run/secrets/minio_webhook_secret
    (el loop *_FILE de Bitnami no cubre MINIO_NOTIFY_*).
  - doc-service: ya montaba el secret; se quitaron las env en claro (el entrypoint exporta
    MINIO_WEBHOOK_SECRET desde /run/secrets/minio_webhook_secret).
  - minio-notify-init: monta `minio_webhook_secret` y usa MINIO_WEBHOOK_SECRET_FILE;
    su script ahora resuelve MINIO_ROOT_PASSWORD_FILE y MINIO_WEBHOOK_SECRET_FILE.

Verificación de propagación (no se imprime el valor):
  $ docker exec infra-minio-1 sh -c 'tr "\0" "\n" < /proc/1/environ' | grep MINIO_NOTIFY_WEBHOOK_AUTH_TOKEN_DOCSERVICE
  -> presente, len=32 (redactado)
  $ docker exec infra-minio-1 sh -c 'wc -c < /run/secrets/minio_webhook_secret'
  -> 33 (32 hex + salto de linea)
  $ docker exec infra-doc-service-1 sh -c 'tr "\0" "\n" < /proc/1/environ' | grep MINIO_WEBHOOK_SECRET
  -> presente, len=32 (redactado)
  Comparación sha256(archivo) = sha256(MinIO PID1) = sha256(doc-service PID1) -> MATCH (3/3)

  $ docker logs infra-minio-notify-init-1
  Target notify_webhook:DOCSERVICE activo -> http://doc-service:8080/internal/storage/events
  Evento ya suscrito en raw-pdfs (arn:minio:sqs:us-east-1:DOCSERVICE:webhook)
  MinIO notificaciones inicializadas.

## S2 — Auditoría y resolución de `infra/compose/mongo/keyfile`
================================================================================
Contenido: 1024 bytes, alfabeto base64 (16 caracteres fuera del charset) -> secreto REAL
(keyFile del Replica Set generado por entorno).
Historial: `git -C infra log --all --full-history -- compose/mongo/keyfile` -> vacío (NUNCA estuvo
trackeado; no hay historial que purgar, la purga queda como N/A).
Clasificación: secreto real de staging (único del entorno, nunca sale del host).

Acción: movido al secret store del host, fuera del árbol del compose:
  $ mv compose/mongo/keyfile secrets/mongo_keyfile
  $ ls -la secrets/mongo_keyfile
  -r--------. 1 999 999 1024 ... secrets/mongo_keyfile   (dueño 999:999, modo 400 preservados)
Compose: `../secrets/mongo_keyfile:/etc/mongo/keyfile:ro`.
`.gitignore`: `secrets/*` lo ignora; ademas `compose/mongo/.gitignore` documenta la reubicacion.
Deuda de doc: `infra/README.md` aún menciona `compose/mongo/keyfile` (README fuera del alcance de
esta tarea; ver riesgos).

## S4 — Rotación practicada en staging: `minio_webhook_secret`
================================================================================
Secreto elegido por bajo blast radius (no toca datos persistidos). Procedimiento del runbook §1.

  $ cp secrets/minio_webhook_secret.txt secrets/minio_webhook_secret.txt.bak
  $ { head -c 16 /dev/urandom | od -An -tx1 | tr -d ' \n'; echo; } > secrets/minio_webhook_secret.txt
  (openssl no está instalado en el host; se usó el fallback /dev/urandom documentado en el runbook)
  $ docker compose ... up -d --force-recreate minio doc-service
  $ docker compose ... up -d --force-recreate minio-notify-init

Verificación (valor redactado):
  - archivo / MinIO PID1 / doc-service PID1 comparten el mismo valor (sha256 MATCH 3/3)
  - minio: Up (healthy); doc-service: Up (healthy); minio-notify-init: target activo
  - Revocación del viejo (POST /internal/storage/events con X-Minio-Webhook-Token):
      token viejo (.bak) -> HTTP 401
      token nuevo        -> HTTP 200
  - Rollback disponible en secrets/minio_webhook_secret.txt.bak

Estado del stack tras la rotación: 16/16 servicios Up (los healthy que aplican).
