## Objetivo

Que Redis Streams deje de ser punto único de fallo: primario `redis-streams` +
2 réplicas + 3 Sentinels (quorum 2), sin alterar el endpoint del cliente en el
perfil `full`.


El log de `sentinel-1` confirmó la conversión del primario anterior a réplica:

```
+convert-to-slave slave redis-streams:6379 redis-streams 6379 @ myprimary redis-streams-replica-1 6379
```

Hallazgo: el primario anterior vuelve como `role:slave`, pero su enlace queda en
`down` porque Sentinel NO propaga `masterauth` al nodo degradado (ver Hallazgo 2).

## Hallazgo 1 — `--replica-announce-ip` es necesario

`sentinel resolve-hostnames yes` + `sentinel announce-hostnames yes` NO bastan por
sí solos. Sentinel descubre las réplicas desde el `INFO replication` del primario,
que reporta IP; al promover una réplica, la anunciaba como IP efímera:

```
[+8s] 172.22.0.12:6379        <- failover con SOLO announce-hostnames (roto)
```

Se añadió a cada réplica del perfil `sentinel`:

```
--replica-announce-ip redis-streams-replica-1     (y -2)
```

Con esto el primario reporta `ip=redis-streams-replica-1` en `INFO replication` y,
tras el failover, los Sentinels anuncian el nombre:

```
[+9s] redis-streams-replica-1:6379    <- failover CON --replica-announce-ip (correcto)
```

Esto cumple el requisito crítico (no anunciar IPs efímeras a los clientes) y es la
causa del fallo clásico de Compose + Sentinel.

## Hallazgo 2 (PENDIENTE de decisión) — `masterauth` en el primario

Al degradarse, `redis-streams` queda sin `masterauth` (a diferencia de las réplicas,
que lo reciben por línea de comandos), por lo que no puede autenticarse contra el
nuevo primario y su enlace permanece `down`:

```
# MASTER aborted replication with an error: NOAUTH Authentication required.
```

Sentinel envía `SLAVEOF` (`+convert-to-slave`) pero no ejecuta
`CONFIG SET masterauth` sobre el nodo degradado.

Prueba del remedio (runtime, NO persistente):

```
$ docker exec infra-redis-streams-1 redis-cli -a *** --no-auth-warning CONFIG SET masterauth ***
$ docker exec infra-redis-streams-1 redis-cli -a *** --no-auth-warning INFO replication
role:slave
master_host:redis-streams-replica-1
master_link_status:up
slave_repl_offset:44744
```

Corrección propuesta (FUERA de la superficie de edición autorizada de esta tarea,
pendiente de aprobación): añadir `--masterauth "${REDIS_STREAMS_PASSWORD}"` (y
opcionalmente `--replica-announce-ip redis-streams`) al comando del servicio
`redis-streams`. En un primario ambas opciones son inertes, de modo que no alteran
el comportamiento observable del perfil `full`.

## 7. Topología final (tras el ensayo)

- Primario (nuevo): `redis-streams-replica-1:6379` — las 3 Sentinels lo anuncian.
- Réplica: `redis-streams-replica-2:6379`.
- Primario anterior `redis-streams`: degradado a réplica de
  `redis-streams-replica-1` (enlace `up` solo tras aplicar `masterauth` en runtime).
- Sentinels: `sentinel-1`, `sentinel-2`, `sentinel-3` en el puerto 26379, quorum 2.

Estado de los 15 contenedores (`docker compose --profile full --profile sentinel ps`):
10 del stack base + 5 nuevos, todos `Up` (`healthy` donde aplica). El stack base
(`--profile full`) permanece sin cambios y saludable.

## 8. Contrato del cliente (P2/P3)

```
SENTINEL_HOSTS=sentinel-1:26379,sentinel-2:26379,sentinel-3:26379
SENTINEL_MASTER_NAME=myprimary
```

Los clientes Sentinel-aware resuelven `myprimary` en cada reconexión (con backoff
+ jitter).

`redis-streams:6379` sigue siendo el endpoint directo del perfil `full` hasta que
P2/P3 adopten clientes Sentinel-aware; este cambio no los altera.
